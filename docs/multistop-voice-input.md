# 多地点导航与语音输入（2026-10-16）

## 多地点能力分析

当前鸿蒙导航已具有“当前位置 → 途经点 1 → 途经点 2 → … → 终点”的连续导航能力。后端返回 `origin/waypoint/destination` 任务，Kotlin 保留途经点顺序，鸿蒙把整个有序列表交给高德 SDK 算路和导航。驾车使用 `calculateDriveRoute`，步行/骑行使用 `calculateWalkRideRouteLatLng`。

| 项目 | MapTemplate | 鸿蒙本轮结果 |
| --- | --- | --- |
| 任务结构 | 有序 `stops`，区分起点、途经点和终点 | 复用同一协议与候选确认流程 |
| 途经点上限 | 对后端声明 10 个 | 从 3 个统一为 10 个，另加 1 个终点 |
| 路线预览 | 相邻地点逐段算路、拼接折线，累加距离/时间 | 使用 SDK 的完整多途经点路线预览，保证预览与实际导航使用同一条已选路线 |
| 实际导航 | 全部途经点一次交给 SDK | 同样由 SDK 连续导航，非应用逐站启动/停止 |
| 地点核对和编辑 | 有 DraftManager 增删方法和地图标记，但 `renderWaypointControls` 目前为空 | Agent 提供有序列表，页面只读展示；通过文字或语音修改行程 |
| 分站执行状态 | 不能仅凭预览拼接认定具有逐站执行器 | 尚无已到站清单、分站 ETA、逐站暂停/继续 |

本机安装的高德 HarmonyOS 11.2.0 `AMapNaviCore.d.ets` 声明驾车和骑步行接口均可传最多 16 个途经点。本应用选择 10 个与 MapTemplate 一致；具体路线可达性仍取决于服务、地点和出行方式。官方接口入口：[IAMapNavi](https://a.amap.com/lbs-dev-yuntu/static/reference/harmonyosnext-sdk/navi/docs/interfaces/api_navi_interface_IAMapNavi.IAMapNavi.html)。网页版本与本地依赖可能不同，编译签名以安装的 SDK 声明为准。

参考源码：MapTemplate `data/route/AmapRouteRepository.java` 的 `calculatePreviewRoute` / `calculateNaviRoute`，鸿蒙 `AmapNavigationEngine.ets` 的 `plan`，共享 `NavigationResponseCoordinator` 和 `NavigationDraft`。

## 本轮补充

- 原生 `NavigationCapabilities.ts` 集中声明上限，Controller、Session、WebSocket 初次绑定/切换会话/提交任务全部采用同一个值；共享层保持相同默认值，以平台环境信息为准。
- 预览页只读展示途经顺序，长列表在有限高度内滚动；没有手动添加、删除、调序和清空入口，共享层也移除了这些操作。地图选点仍用于修改终点，不会添加途经点。Agent 确认新行程后使旧路线失效并重新算路，防止继续启动旧路线。
- 统一校验数量、坐标及名称；拒绝相邻重复站点，保留非相邻重复地点，以支持合理往返。不会自动去重或重排用户行程。
- navi-claw 原 `clampWaypoints` 会直接截断超出上限的途经点。本轮改为现有协议的 `unsupported` 响应，说明实际数量和客户端上限，`task_complete=false` 且不提供可执行任务，不覆盖原任务。未声明上限的旧客户端保持兼容。

**前一轮的后端超限校验改动需要同步部署才会生效**，只修改和验证源码，未部署服务。文件为 `navi-claw/src/domains/navigation/postprocess.ts` 与对应协议测试。示例：超过 10 个途经点的请求应明确提示缩减行程，不得悄悄少走几个地点。

## 多轮候选确认与超时修复

对照 MapTemplate 的 `NaviClawChannelClient`，Android 只对连接和写入设置 30 秒超时，导航处理没有固定 30 秒截止；鸿蒙旧实现却从连接前开始计时，30 秒后删除 pending，迟到的候选和路线回复都会被丢弃。后端多地点解析包含多次模型/POI 搜索，可以超过这个预算。

- 导航处理等待方式与 MapTemplate 对齐，不再用 30 秒报处理失败。连接、写入和会话绑定仍分别处理失败和超时；等待时保留进度及取消入口。不依据无关通知重置计时，不自动重发已发送意图。
- 导航帧使用真实 requestId 管理队列；取消后不再发送过期队列项，写入失败直接报错，避免请求被静默留在队列。
- 复用后端 `partial_task/candidate_groups`：按最小 `for_stop_index` 展示当前组，每次只提交该组选择，等待后端返回剩余组；全部确认后才执行完整路线。已确认的途经点顺序由后端维护。
- 当前候选卡在等待和异步错误时保留，收到下一组后重建卡片；防止连续点击、旧卡片事件串到下一组。页面展示已确认地点和待选数量，候选较多时滚动显示。服务端明确报告候选失效时，应按错误提示重新提交行程，而不是自动重复选择。

本轮无需修改 navi-claw 接口。服务端的候选确定性处理见 `src/domains/navigation/disambiguation.ts`：选中的 POI 写入对应站点，只返回未确认组，最后返回完整任务。后端现有单次响应最多 4 个候选组，与客户端最多 10 个途经点是两个不同限制；本次没有扩大后端的候选组上限。

## 语音输入流程与分层

按最新真机反馈调整：识别结果实时展示，成功结束后自动发送后端，并在输入框保留识别原文。

1. 点击“语音”收起键盘，首次按系统流程申请麦克风权限；按钮显示“准备中”，这时不会显示红色录音状态。录音器已启动且收到至少约 100 毫秒音频后，才显示“正在聆听”和“结束”。准备阶段重复点击不会误结束录音。
2. 输入框在录音和等待最终结果时都可编辑、发送，实时文字显示在输入框上方。用户改过的地点语句受到保护，未改语句允许最终纠错，通过标点或明确连接词表达的后续口述继续合并；没有明确边界的冲突保留用户文字，不把两个地点拼成一个名称。整框清空保持空白，避免旧识别内容重新填回。再次点击“结束”停止录音，等待最终结果时仍可编辑或点击“取消”。
3. 未手工修改的语音文本点击“发送”，先停止录音并等待最终结果，再走原有发送流程；不会直接取消识别并提交临时半句。已手工编辑的文本点击“发送”视为明确确认，立即以当前文字提交并取消剩余识别。两条路径均只提交一次；正常结束仍自动发送确认后的结果，输入框保留原文。准备期间已有文字可直接发送，空输入不会发出请求。
4. 取消时保留手动修改；没有手改时恢复录音前文字。识别失败或最终结果未确认时，保留已识别草稿并提示原因，不自动发送。无识别内容时不清空旧输入。切换到“我的”、进入登录页、系统返回、切后台或销毁页面都会取消录音。
5. 请求和算路期间继续展示原文摘要与简短进度，Agent 确认终点/途经点以及候选确认后不再把原文覆盖为终点名称；结束后输入框仍可编辑。

| 层级 | 代码 | 责任 |
| --- | --- | --- |
| 共享页面 | `NavigationPage.kt` | 麦克风按钮、实时文字、回填、复用发送入口、页面切换取消 |
| 共享业务 | `navigation/voice/VoiceInputCoordinator.kt` | 准备/聆听/结束等待/空闲状态、用户编辑与语音合并、等待最终结果、完成回调一次、隔离迟到事件 |
| 地名上下文 | `presentation/NavigationVoiceLexicon.kt` | 当前行程、候选名称和本次页面内最近确认地点的有限热词列表 |
| 共享桥接 | `NavigationVoiceModule.kt` | 传递 `subscribe/start/stop/cancel/unsubscribe` |
| 鸿蒙模块 | `KRNavigationVoiceModule.ets` | 命令转发和事件订阅 |
| 鸿蒙语音服务 | `HarmonyVoiceInput.ets` | 权限、录音器、语音识别器、超时、资源释放 |

桥接使用 `requestId` 关联每次录音，事件携带 `state/text/isFinal/error`，`start` 可携带 `hotwords`。录音期间使用独立 `voiceActive`，仍阻止选点及切换会话；`canSendInput` 单独允许编辑和发送。`takeForSubmit` 返回空表示正在等待确认结果，成功后先释放语音状态，再由原 `canSubmit` 请求门控接管。用户已确认的手工文本则立即释放语音状态并发送。

平台采用系统 [Core Speech Kit](https://developer.huawei.com/consumer/cn/sdk/core-speech-kit/) 的普通话离线识别，不新增高德/讯飞/云语音 Key。按本机 SDK 明确支持的接口，使用 AudioCapturer 采集 16 kHz、16 bit、单声道 PCM，并按 640 字节分包输入识别器。分句结果累计，停止录音后调用 `finish` 等待最终结果；55 秒自动结束，启动和结束等待均有超时。录音不写入文件，也不上传 navi-claw；成功结束后提交识别文字。

原生端接受启动窗口的音频，结束时在录音器停止完成前继续接收尾帧，补齐末包并送完再调用 `finish`。640 字节音频以约 20 毫秒节奏排队发送。已确认子句与临时子句分开维护，空的结束标志不能把临时文字变成最终结果；移除 `onComplete` 后固定 500 毫秒强行封口的逻辑，保留有界等待，未确认草稿不自动发送。

识别引擎和采样参数未变更。热词通过本机 SDK 声明的 `sysGeneralLexicon` 接入，每词 2–20 字、去重、最多 200 个；不截断长地名，不从会话散文中猜测地点，不硬编码城市。最近地点仅保存在页面内存，退出登录或页面销毁清空。无须填写新 Key。

诊断使用 HiLog 的 `NaviVoice` 标签，仅记录录音/识别时序、音频字节数、音量统计、最终结果标志与错误码，不记录录音或识别文字。真机失败时应先区分没有音频、接近静音、有声但无结果、最终结果超时。`first_frame/listening_ready/finish_requested/confirmed` 可以定位开始与结束过程；`inputBytes/sentBytes/peak/rms/isFinal/isLast` 可以区分采集和识别结果问题。近静音判断用于错误说明，不拒绝识别器已经返回的文字。Kuikly 输入事件未提供可信的变更来源，迟到程序回声只能做有限历史防护，不能宣称完全区分所有人为撤回与程序回声。

设备需要具备系统语音识别能力与可用的离线模型。系统能力缺失、权限拒绝、识别失败会明确提示，可继续文字输入。远程测试机是否能接收测试端麦克风音频，需要由测试平台实际验证。

录音时暂停高德内置播报并中断当前播报，结束时仅在导航仍运行的情况下恢复；页面隐藏、退出和异常关闭都释放录音器与识别引擎。权限尚未返回或引擎尚未创建时取消，也不会由迟到回调重新启动麦克风。

## 尚需后续补齐的多段能力

- 接入 `onArrivedWayPoint` / `onArrivedTravelWayPoint`，在共享层维护已到站、当前站、下一站。
- 导航中修改任务和退出后重新算路时只保留未经过的站点。**当前仍会保留原途经点列表**；若已走过部分站点，应通过文字或语音告知 Agent 跳过这些站点，待新行程确认后再规划。
- 增加每段距离/预计到达时间，以及逐站停留、暂停/继续和中断恢复。如果未来需要不同路段采用不同出行方式，再引入独立的分段任务执行器。

这些能力不能通过“支持多个途经点”自动推导，本轮不把 SDK 最终到达事件当成中途站点到达。

## 真机复测

1. 输入“先去 A，再去 B，最后到 C”，确认列表为 A、B，终点 C；三种出行方式分别核对算路和真实/模拟导航。
2. 确认没有手动途经点按钮；向 Agent 请求删除、调序或取消全部途经点，确认新行程生效后路线重算，旧路线不能启动；验证 10 个途经点边界及 11 个途经点明确拒绝。
3. 两次相邻相同地点应提示调整；非相邻往返不得被静默删除。
4. 首次拒绝/允许麦克风权限；连续点击开始/结束；无声音、分句、多地点长句、识别错误后重试。
5. 确认说话时文字逐步更新，结束后自动请求一次，输入框保留完整句子；录音时切换登录页、底部 Tab、返回、切后台，麦克风应停止，不能自动发送，迟到文本不能覆盖新输入。未登录、会话切换中、后端失败时保留识别文字并提示原因。
6. 导航播报期间启动录音，确认播报暂停、导航进度继续、识别结束后播报恢复；取消导航后不可恢复播报。
7. 录音中修改一个识别错字，再说“然后去……”确认修改保留且下一站继续回填；例如将“去车站北广场”改成“去车站南广场”，继续说“然后去公园”，不能出现“南广场北广场”。手改后点击发送应立即提交当前文字；未手改时点击发送应等待最后纠错，后端均只收到一次且输入保留。清空后结束不发送；最终识别等待期间也能编辑并确认发送。
8. 用含多个同名地点的句子请求行程，依次确认途经点和目的地，确认已选地点不会丢失、全部确认前不算路。弱网导致确认失败时候选仍在；后端超过 30 秒返回时仍能接收，取消后的迟到回复不能复活旧任务。
9. 麦克风未就绪时按钮显示“准备中”，不能误认为已开始聆听；无音频、静音、有声音但无文字应给不同提示。最终识别超时时保留草稿、没有后端自动请求，可修改后手动发送。DevEco 日志用 `NaviVoice` 标签筛选采音与识别指标。

自动测试和编译不替代真机语音识别效果、麦克风输入、地图叠层及多站道路导航验收。
